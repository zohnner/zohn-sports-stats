# SportStrata — Site Improvement & Monetization Roadmap
**Owner:** z man | **Drafted:** 2026-08-08 | **Built from:** `docs/full-audit-2026-08-08.md`, `DECISIONS.md` D-069/D-070/D-072, `ISSUES.md`'s three paid-tier specs, `GOALS.md`'s Monetization section, `docs/sponsorship-outreach.md`

**What this is:** a single sequenced plan, not two separate ones. The two revenue tracks (subscription, ads/affiliate) and the technical-debt items from the audit are interleaved deliberately — several audit findings are on the critical path to monetization, not parallel busywork, and the plan says explicitly which is which.

**The one-sentence version:** the subscription tier is closer to revenue than it looks (three features spec'd or half-built) but Stripe itself hasn't been started at all; the ad/affiliate track is farther than it looks (blocked on traffic data that only started collecting 2026-08-09). Sequence: harden the money-handling code first, ship Stripe + the subscription tier ahead of the Sep 10 NFL kickoff window, let traffic data accumulate in parallel, then pursue ads once there's a real number to put in an application.

## Phase 0 — Harden before money moves through the code (start immediately, ~1–2 weeks)

This phase exists because the audit found the exact gap that matters most right before Stripe gets wired in: `security.md`'s threat model doesn't know payments exist yet, there's no CI gate, and there's zero test coverage on the session/entitlement layer the whole subscription tier depends on. Doing this after Stripe ships means the first real security review of a live payment integration happens after it's live. Doing it now costs less and closes the gap before it matters.

1. **Refresh `security.md` and `dev.md`'s Project Context Blocks.** (Cipher/Axiom, audit finding, ~30 min each) `security.md` currently states "Auth mechanism: None. Fully public site" — a Stripe integration should not be built while the persona responsible for threat-modeling it is working from a file that doesn't know sessions or a user database exist.
2. **Wrap the existing 13 `/deploy-check` checks in a required GitHub Actions workflow.** (Axiom, audit A1) The checks already exist and are well-designed; this is invocation, not redesign. Do this before Stripe code starts landing, so the webhook handler and Checkout wiring ship under a real gate from their first commit, not retrofitted later.
3. **Add test coverage for `functions/api/_entitlement.js` and the write path it depends on**, before the Stripe webhook is built on top of it. (Axiom, audit A2) This is the one place "zero tests" and "this code will soon control who gets charged and who gets access" overlap directly — it's worth being the first file in the repo with real coverage, not an afterthought once Stripe lands.
4. **Fix `DESIGN.md`'s `--color-live` entry and `design.md`'s `--accent` value.** (Kael, audit K1/K2) Five-minute, zero-risk fixes. No reason to sequence them later — do them this week so they're not still open the next time someone reads either file.
5. **Decide the `--accent`-on-`--accent-subtle` contrast WARN.** (Kael, audit K3) It's been re-flagged three-plus cycles running; a decision either way is cheaper than another re-flag, and a paid product should not launch with a known, unresolved WCAG contrast gap on a live token.

None of Phase 0 blocks Phase 1 from starting — pricing and Stripe scoping can happen in parallel with items 1–5.

## Phase 1 — Ship the subscription tier ahead of NFL kickoff (target: live before Sep 10, 2026)

**Why this date, specifically:** `functions/api/*`'s own season model (`_nflKickoffDate()`) puts the 2026 NFL regular season's first game on the Thursday after Labor Day — **September 10, 2026**. `ISSUES.md`'s own AI League Insights spec says the quiet part out loud: insight quality depends on real in-season signal (live trending, real injury designations, real matchups) that doesn't exist during preseason. Shipping the paid tier before kickoff means it's live and already generating real insights the moment the audience that would pay for it — active fantasy managers making Week 1 decisions — shows up in volume. Shipping it in October means missing the single highest-intent window of the fantasy calendar.

**Step 1 — Owner pricing decision (blocks everything else in this phase).** This is a real business call and genuinely not mine to make unilaterally, but I'll give a concrete starting recommendation rather than leaving it fully open, since "figure out pricing" with no anchor tends to stall: **$4.99/month or $29/year**, single tier, no feature-gated sub-tiers. Reasoning: the comparable market (FantasyPros MVP, ESPN Fantasy+) sits in the $8–13/month range for a broader bundle across more sports and more tools; SportStrata's v1 paid surface is three specific features on one sport's fantasy layer, not a full suite, so pricing at roughly half the category norm reflects the smaller bundle honestly rather than trying to extract full-suite pricing for a first release. A single tier (not "Basic/Pro/Enterprise") also matches the product's existing anti-complexity posture (`DESIGN.md`'s restraint principle) and avoids re-litigating the old, retired R1–R5 tier structure that `GOALS.md` explicitly walked back as premature. Revisit the number after the first month of real conversion data — this is a starting point, not a permanent commitment.

**Step 2 — Build Stripe integration (net-new work, not wiring).** Per `ISSUES.md`'s own feasibility note: Stripe Checkout (hosted page, SportStrata's code never touches card data), a webhook handler at `functions/api/stripe/webhook.js` (signature-verified, upserts the already-existing `subscriptions` table), and the upgrade CTA already speced in each of the three feature entries. This is real, scoped, buildable work — the D1 schema and the `isEntitled()` read-side are already correct and waiting; only the write side (webhook) and the purchase flow (Checkout) are missing.

**Step 3 — Finish and verify the three already-spec'd features.**
- **Personalized Fantasy Grade** and **Weekly Fantasy Digest** are marked "implementing this pass" in the source log — confirm both are actually complete and live-verified (not just started) before counting them as shippable.
- **AI League Insights** has a landed spec and zero implementation — this is the one that needs a real build pass, using the exact Gemini + Workers-KV pattern already proven live in production for Broadcast Blurb (D-068), per its own feasibility note.
- Verify all three respect the free-tier allowances specified (one insight/week free, grade letter free, unlimited/full-breakdown paid) — these aren't optional polish, they're the actual product-market test of whether the paywall line is drawn in the right place.

**Step 4 — Ship, then watch the free/paid split for the first real signal.** The free tier isn't a teaser — it's a real weekly value delivery per the spec (`ISSUES.md`: "a real taste of the feature, not a teaser screenshot"). Whether free users convert or stay comfortably on the free allowance is the actual answer to whether $4.99/mo is priced right, and it's a better data source than any amount of upfront analysis.

## Phase 2 — Ads and affiliate revenue (parallel track, starts now, converts to cash later)

This doesn't block on Phase 1 finishing — it blocks on time and data, so the clock should start today even though the payoff lands later.

1. **Let Cloudflare Web Analytics accumulate real numbers.** No action needed beyond waiting — but don't apply to any ad network before there's at least 3–4 weeks of real traffic data to report; a Day 2 application with no numbers will just get a form-letter rejection or a lowball rate.
2. **Once real numbers exist, apply to Path A (Playwire first, then Raptive/Mediavine if traffic clears their thresholds).** Lowest friction, no licensing exposure, fastest path to any revenue at all. Use the pitch template already drafted in `docs/sponsorship-outreach.md` — just needs the traffic blank filled in.
3. **Path B (sportsbook CPA affiliate) sequenced behind Path A, not parallel.** Real legal review is a genuine prerequisite before signing anything, per the licensing research already done — this isn't a step to rush to catch the NFL season. It's fine, and arguably better, if this lands in Q4/Q1 rather than September.
4. **Sequence Path B deliberately against the app-store plan (D-066).** `docs/sponsorship-outreach.md` already flags this: a live sportsbook affiliate placement can complicate Android/iOS store review. If the Android TWA submission (D-066, low-effort, foundation already built per that decision) happens first, do it before a sportsbook placement goes live, not after.

## Phase 3 — Site-quality work that directly supports monetization (not general hygiene)

These are pulled from the audit but re-sequenced here specifically because they affect whether a paying or ad-supported audience trusts and stays on the product — general technical debt that doesn't touch revenue (e.g. the `mlb.js` line-count split) is left for a normal engineering pass, not listed here.

1. **A scoped WCAG audit before the paid tier's first real cohort of paying users hits it.** (Vera, audit V3) The audit already found the accessibility backlog has roughly doubled since the last scoped pass; shipping a paywall in front of an unaudited surface is a worse look than shipping it in front of a free one.
2. **Live click-through verification as a standing rule for every new interactive control**, not deferred to whoever happens to click it next. (Vera, audit V2) The account-menu bug sat live for weeks; a Checkout button with the same class of bug would cost real money, not just a bad click.
3. **CI gate and auth test coverage (Phase 0, items 2–3) are the real prerequisite here** — repeating only to make explicit that Phase 3's "trust" framing and Phase 0's "harden" framing are the same work, not two different lists.
